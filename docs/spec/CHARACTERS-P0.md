# 三角色形象系统 + 训练模块拆分 + Rive 动效（增量 PRD）

> 增量范围：**只改三件事** —— ①角色从"一个咕嘎"变成"三选一 + 各自形态"；②训练 Tab 与训练记录页分家；③接 Rive 动效（含降级）。
> 数据层仅新增 **1 列**（`user_settings.character_id`），不新增表、不新增 pub 依赖（除 `rive` 本身）。
> 本文对齐 `PROJECT.md`（减脂优先 / 无手动版本号 / 300 行纪律）、`DEVELOPMENT_PLAYBOOK.md`（异步一律 Riverpod、迁移铁律、check.sh 门禁）、
> `docs/spec/COACH-P0-ENGAGEMENT.md`（写法与颗粒度：每条规则必须能被一条测试证伪）。

## 0. 文档约定

### 0.1 本期三个硬边界

1. **不扩功能面**。本期不新增"选形象"引导页、不做时长选择器、不做角色语音、不做配饰养成、不做角色亲密度/能量值。要扩先改本文。
2. **不动教练内核**。`aiStyle` 四风格、personaLines、工具清单、`writeTools` 逐次确认、记忆与主动消息全部原样。角色换名字**不等于**换教练（见决策 7）。
3. **动效不是必需品**。`.riv` 是可选增强，缺了就得能用 —— 这条决定了 R 组所有规则的方向：**降级路径必须先做完、且和 Rive 路径行为等价**，再谈 Rive。

### 0.2 计数口径

- 规则编号与验收编号**一一对应**（`C7` ↔ `C-7`）。规则表说"要什么"，验收表说"怎么证伪"。
- 优先级：**P0 = 本期必须做且必须可测；P1 = 结构留好、本期不做；P2 = 只记录**。
- 「形态」= 一个角色内部的样子档位（咕嘎 3 档 / 糯糯 3 档 / 菲比 1 档）；「角色」= 咕嘎 / 糯糯 / 菲比。**用户向文案里不出现"形态"二字**（见决策 5）。
- 「累计减重」= 起始体重 − 当前体重（斤）；「历史最大减重」= 起始体重 − 历史最低体重（斤）。两者都从 `body_metrics` 现算，不落库。
- 本周 = 周一 00:00 起算，与 `workout_list_page.dart` 现有周视图一致。

## 一、背景与问题

三个问题，都是"已经在用、但明显不够"的地方：

| 问题 | 现状证据 | 用户感受 |
|---|---|---|
| **只有一个形象，且不能换** | 形象写死为咕嘎 3 阶段（`guga_level.dart`），全 App 4 处渲染咕嘎（首页角色区、首页小头像、趋势页卡、聊天页头像）。不喜欢鸟的用户没有任何出口 | "这 App 的吉祥物我不熟，也不想熟" |
| **训练 Tab 名不副实** | 训练 Tab 打开是"训练记录"（看过去），真正的"现在练什么"藏在 FAB 和二级页里；同时"历史"又是训练页的第三个分段 —— 同一份数据两套列表 | "点训练，先看到一堆历史，我得再点一下才能练" |
| **动效是代码画的** | `guga_puppet.dart` 靠 `Transform.rotate` + `math.sin` 模拟摆头与呼吸；想加一个挥手动作就得再出一张 PNG（现有每阶段 2 张：待机 + 动作帧） | 动作只有"整图切换"这一种，看起来是幻灯片不是动画 |

**为什么现在做**：
1. 三张角色设定稿已经出好了（抠图完成），素材是沉没成本，不做就是浪费。
2. 训练页那套"两份列表"的口径分歧已经发生（N 组 vs N/M 组），越晚拆越容易在别处复制第三份。
3. Rive 接入本身**不阻塞**任何东西 —— 因为降级路径先做完就能上（R 组的设计前提）。

## 二、目标 / 非目标

### 2.1 目标（3 个，正交）

1. **让用户能挑一个自己愿意天天看见的形象，并且换角色的代价是 3 次点击、即时生效、不用重启。**
2. **让"训练"Tab 只回答一个问题：现在练什么。** 过去的训练有独立的地方看，且只有一个地方。
3. **让角色动起来这件事变成"替换文件"而不是"改代码"**：`.riv` 在，Rive 播；`.riv` 不在，程序化动画顶上，两条路径用户看到的交互完全一致。

### 2.2 非目标（明确不做，别顺手加）

| 不做 | 理由 |
|---|---|
| 首次启动选形象引导页 | 多一个阻断式页面，收益是"用户可能选一次"；而"我的 → 我的形象"随时能进。P1 |
| 训练时长选择器（10/5/23 分钟三档） | 现有代码里不存在这个东西，本期也不发明（决策 9） |
| 角色配音 / 角色语音台词 | 与"换个形象"无关，`flutter_tts` 已有语音教练，别混在一起 |
| 配饰、亲密度、养成值、角色换装 | 需要新的状态与素材体系，本期只要"能选 + 会变" |
| 手动选形态（"我就要小咕嘎"） | 形态是减重成果的可视化，能手动选就等于把它作废（决策 4） |
| 糯糯/菲比的头身拆分图与分层动画 | 需要重新抠图出 6 张；先走单图降级，P1 可加文件生效 |
| 训练页重做模板卡 UI | 卡片已经能用，本期只做结构搬移，不重画 |
| 记录页做图表 | 图表在 `/workout/stats`，两个页面各管一件事 |
| 动效降级时提示用户 | 见决策 15 |

## 三、用户故事

1. **换形象**：As 一个从第一天就不喜欢那只鸟的用户，I want 在"我的"里两下点到一个形象页，看到糯糯长什么样、点一下就换成她，so that 我明天打开 App 看到的不是一只我不想看的鸟。
2. **变样子**：As 一个累计减了 2 斤的用户，I want 糯糯某天换了个样子（蓝发版），并被告知"解锁了一个新样子"，so that 我知道自己在往前走，但 App 没有对我的身材下判断。
3. **掉秤又回来**：As 一个上周水肿涨了 1 斤又掉回去的用户，I want 我的角色不要因为这一斤退回上一档，so that 我不会觉得 App 在说我胖了。
4. **现在练什么**：As 一个下班到家、只有 15 分钟的用户，I want 点训练 Tab 直接看到能开练的模板，so that 我不用先穿过一堆历史记录。
5. **看看练了多少**：As 一个想知道"这个月我到底练了几天"的用户，I want 从训练页右上角或"我的"里进到训练记录，按周翻、点某天看当天练了什么，so that 我不用在一个页面里既找训练又找记录。
6. **再练一次**：As 一个上周练过一次很顺的模板的用户，I want 在记录详情里点"再练一次"就带着同样的动作和组数开始，so that 我不用重新挑一遍动作。
7. **动不起来也不难看**：As 一个 `.riv` 还没做好（或加载失败）的用户，I want 角色照样呼吸、照样点一下就回应我，so that 我不会看到一个白框。

## 四、产品决策（17 条，对应任务书 A/B/C 三组 17 问）

> 编号即问题编号：D1 ↔ A1 … D17 ↔ C17。每条给结论、理由、反面。

### 决策 1（A1）· 切换入口：**我的 → 我的档案 → 「我的形象」独立页；首页长按角色为隐性快捷入口**

**结论**

| 入口 | 位置 | 路由 | 显性程度 |
|---|---|---|---|
| 主入口 | 我的 → 我的档案 → 「我的形象」 | push `/settings/character` | 显性，名字写清 |
| 快捷入口 | 首页长按角色本体 500ms | push `/settings/character` | 隐性，不做任何引导 |

**理由**
- 「我的形象」是身份类设置，和「个人档案」「身体相册」同一层语义，放这一组用户找得到（`settings_page.dart` 的「我的档案」段已有 3 个 tile，加第 4 个不需要重构）。
- **明确不放教练设定**：`/ai/settings` 只有聊天页右上角一个入口（`ai_chat_page.dart:172`），用户要换形象得先进聊天 → 换形象成了"调 AI 参数"的副产品，语义错位，且路径是 3 层。
- **不放首页按钮**：首页首屏的预算已经给光了（生病横幅 + 问候 + 195px 角色 + 教练气泡 + 今日任务 + 照片对比）。再加一个"换装"按钮，抢的是"点角色"的热区。
- 长按是白送的（`GestureDetector` 加 `onLongPress` 一行），但**不做提示**：做得出来的隐性通道，提示出来就变成显性按钮的替代品，反而占位置。

**反面**
- 挂在教练设定下：用户想问"我能换个形象吗"，答案在"点角色 → 进聊天页 → 右上角设置 → 往下滚"。绝大多数人找不到，功能等于没做。
- 首页放按钮：首屏每加一个元素，角色的视觉重量就掉一档。而角色是本期的主角。

### 决策 2（A2）· 生效时机：**即时生效，不重启；正在播的动作帧直接丢弃回待机**

**结论**

| 项 | 结论 |
|---|---|
| 生效方式 | 写库 → `ref.invalidate(userSettingsProvider)` → 首页角色就地重建 |
| 是否重启 | 否，也**不提示"重启后生效"** |
| 旧动作帧 | 丢弃，回待机（不跨角色/跨形态续播） |
| 过渡动画 | 无（直接换图），换完 1.5s 内角色说一句「我是糯糯」（见 6.3），之后恢复通用台词 |

**理由**
- 动作帧（PNG 动作帧或 Rive state）是绑在**旧资源**上的：旧角色的 `tap_react` 播到一半换图，等于新角色做旧角色的动作，最坏情况是 Rive 换文件时 controller 还持有旧 artboard 引用 → 花屏或空帧。
- 本 App 所有设置（主题、语速、提醒）都是即时生效。唯独形象要重启，用户第一反应不是"设计如此"，是"没成功"，然后连点两次。
- 切形象可随时换回来，成本为零，**不需要二次确认**（与 COACH-PRD 决策 6「删单条记忆不二次确认」同一逻辑：回到安全态的操作不该被拦）。

**反面**
- 重启生效：给了用户一个"没生效"的错觉，还额外需要一个"已保存，重启后生效"的提示条 —— 用一个提示去解释一个不必要的行为。

### 决策 3（A3）· 存储：**`user_settings.character_id` 一列，`NOT NULL DEFAULT 'guga'`**

**结论**

| 项 | 结论 |
|---|---|
| 存放位置 | `user_settings.character_id`（TEXT） |
| 默认值 | `'guga'` |
| 老用户升级后 | 咕嘎（= 现在那只鸟，不换脸） |
| 新装用户 | 咕嘎（本期不做首启选择器） |
| 非法值（空串 / 大写 / 中文 / 未来版本才有的角色） | 运行时按 `guga` 渲染，**不回写数据库** |
| 清空全部数据后 | 回 `guga`（`user_settings` 已在 `DataWipeService.tableNames` 里，天然覆盖） |

**理由**
- 单用户、单值、无历史需求（"我上个月用哪个形象"没有产品价值）。新表要一套 entity/repo/CRUD + 一个 JOIN，换来的是零。
- 默认咕嘎：老用户升级后突然换脸，是惊吓不是惊喜；咕嘎也是当前 App 图标与通知标题里的那只。
- **非法值不回写**是一条硬规则：假设用户在新版本选了"某第 4 个角色"，又装回旧版本 —— 旧版本渲染咕嘎是对的，但如果它把 `character_id` 覆写成 `'guga'`，用户再升回新版本时就永久丢了自己的选择。**降级可以显示错，但不许改数据。**

**反面**
- 新建 `characters` 表 + 用户-角色关联表：为解决一个"选一个值"的问题引入两张表，还要考虑外键与清空顺序，纯负债。
- 用 SharedPreferences：本 App 所有用户偏好都在 `user_settings`，另起一个存储源 = 数据管理页导出/恢复时要多记一处（`data_management_page` 与备份 manifest 都会漏）。

### 决策 4（A4）· 形态与冲突：**形态不可手动选；口径改成"已达最高形态"，只升不降**

**结论**

| 项 | 结论 |
|---|---|
| 形态是否继续自动按累计减重 | 是，阈值沿用 0 / 2 / 5 斤（`guga_level.dart` 不改数值） |
| 能不能手动选形态 | **不能**。UI 上不出现任何"选形态"控件（选的是角色，不是形态） |
| 冲突规则 | **冲突不存在**（因为不能手动选）。但把口径从"当前累计减重"改成"**历史最大减重**"，形态只升不降 |
| 历史最大减重怎么算 | 起始体重（最早一条 `body_metrics`）− 历史最低体重；纯函数，不落库 |
| 删记录导致回退 | 允许（自愈）。删掉最低点记录后形态可能回退，不做补偿 |

**理由**
- 形态是"减重成果的可视化"，是这套系统唯一的意义。一旦允许手动选，用户会立刻选第三档，然后这个功能就和减重彻底脱钩了。
- 体重日间波动 ±1~2 斤是正常的（水、盐、碳水、排便）。按实时值算，用户会看到自己的形象在「普通咕嘎」和「肥咕嘎」之间横跳。**那不是"数据在波动"，那是 App 在说他胖了。** 只升不降一次解决这个问题。
- 零新增字段：`start = 最早记录.weight`、`minLoss = start − allMetrics.min(weight)`，两个聚合就能算。为它加一列"已达成形态"是不必要的持久化（还得处理"删记录后这一列怎么办"）。

**反面**
- 按实时值算：一顿火锅后角色退档 → 用户骂的不是"水钠潴留"，是"这 App 是不是在嘲笑我"。这是把一个激励设计成一个羞辱。
- 加"已达成形态"列：多一列、多一条与 `body_metrics` 可能不一致的冗余真相（COACH-PRD 决策 5 的老教训：重复存储必然和真数据打架）。

### 决策 5（A5）· 糯糯三张画风不一致怎么说：**概念叫「样子」，形态名只描述外观，禁止身材评价词**

**结论**

| 项 | 结论 |
|---|---|
| 用户向概念词 | **「样子」**（不用"形态"「阶段」「等级」） |
| 代码/文档词 | 形态（`form`） |
| 咕嘎三档名 | 沿用现值：**肥咕嘎 / 普通咕嘎 / 小咕嘎**（不改） |
| 糯糯三档名 | **糯糯（玩偶版）/ 糯糯（蓝发版）/ 糯糯（灰发版）** —— 只描述材质与发色 |
| 菲比 | **菲比**（单形象，无档名） |
| 解锁/切换文案 | 只允许「换了个样子」「解锁了「糯糯（蓝发版）」」 |
| 禁用词 | 瘦了 / 变瘦 / 苗条 / 胖了 / 减肥形态 / 瘦身版（写进常量并有测试，见 C9） |

**理由**
- 糯糯的三张图**不是同一套画风**：毛绒玩偶（3D 毛发质感）→ 蓝发 2D → 灰发 2D。说成"瘦了"会让用户盯着图找"哪里瘦了"，找不到就归因为"画崩了"。
- 说成"换了个样子"就是"换装"：用户不会追问形态与体重的因果关系，只会记住"往前进了一格"。
- 咕嘎的名字**不动**：它是品牌资产（App 图标、通知、现有用户认知），改文案的收益远小于风险。而且"肥咕嘎"说的是角色，不是用户。
- 糯糯的名字里**不许出现"肥/小"**：「肥糯糯」听起来是在说用户。

**反面**
- 「你瘦了，糯糯也变苗条了」→ 用户放大看蓝发版，找不到瘦在哪 → 认为素材做坏了。
- 糯糯也叫「肥糯糯 / 小糯糯」→ 和咕嘎的档名复用，用户会以为三个角色共用一套身材说法，然后拿玩偶版的"肥"去对照自己。

### 决策 6（A6）· 菲比单形象靠什么体现"我在变好"：**台词分档，零新素材**

**结论**

| 项 | 结论 |
|---|---|
| 方案 | 同一张图 + 三档台词池（阈值同 0 / 2 / 5 斤） |
| 数据结构 | 菲比 `forms` 只有 1 项（`form` 恒 = 1），但 `lineTier` 仍按历史最大减重算 1/2/3 |
| 台词量 | 每档 ≥3 句（定稿见 6.3） |
| 是否影响其他角色 | 咕嘎/糯糯同样走 `lineTier` —— 台词按档取是**共用机制**，不是菲比特例 |

**理由**
- 零新素材、零新字段、零新渲染分支，只有一个常量表。
- 台词是这套系统里**唯一**能承载"我注意到了你的进展"而不需要美术成本的地方。
- 把 `lineTier` 做成三角色共用，避免"菲比走一条特殊路径"这种将来没人敢改的分支。

**反面**
- 配饰叠加（每档一套 PNG）：3 张新素材 + 一套叠加渲染 + 一套位置/缩放校准（每个形象的头身比不同），成本是台词的 20 倍，收益是"用户可能没注意"。
- 背景色随档变：会和 `AppColors` 的主题色打架，用户第一反应是"这页是不是渲染错了"。

### 决策 7（A7）· 教练要不要跟着变：**教练名不变、人设不变，只有"称呼"变**

**结论**

| 项 | 变不变 |
|---|---|
| 教练名字「嘎教练」 | **不变**（通知标题「嘎教练说」也不变） |
| `aiStyle` 四风格 / personaLines / 输出格式 | **不变** |
| 工具清单 / 写操作确认 / 记忆 / 主动消息 | **不变** |
| 角色头像（首页小头像、趋势页卡、聊天页头像） | 变（跟着 `character_id` + 形态） |
| system prompt 里提到角色时的名字 | 变：注入一行 `【陪伴角色】<名字>。提到它时用这个名字，不要叫咕嘎` |
| 教练自称 | **禁止**自称角色名（写进同一行） |

**理由**
- 教练是**产品人格**（"嘎教练"是这个 AI 的名字，跟用户无关），角色是**用户选的形象**。两者解耦，才不会出现"换了糯糯，AI 开始说'我是糯糯'"。
- 只有一处必须跟着变：AI 提到"你的咕嘎"时得说"你的糯糯"。不改这一行，用户在糯糯的形象下收到「咕嘎陪你一起」，会觉得整件事是半成品。
- 「嘎教练说」不改名：会牵扯通知渠道名、4 处文案、persona prompt 的角色句、以及用户对"我的教练叫什么"的既有认知；换来的只是名字上的一致感。

**边界（避免人设混乱，写死）**：**角色以第一人称说的是"角色台词"（首页角色气泡），教练说的是"教练的话"（`CoachWeeklyBubble` 教练气泡 + 聊天页）。两个气泡不是一个说话人，文案不许互相挪用。**

**反面**
- 教练跟着改名（"糯糯教练"）：通知标题、persona 段、记忆留痕文案全得改；用户会怀疑"换形象是不是把教练的记忆也清了"。
- 完全不注入角色名：AI 在糯糯面前叫用户"咕嘎"，或在描述陪练时说"咕嘎在旁边" → 人设裂开。

### 决策 8（A8）· 资源缺失兜底：**三层静默降级，不弹窗、不写库**

**结论**

| 层 | 触发 | 表现 |
|---|---|---|
| 1 | `.riv` 缺失 / 损坏 / 不兼容 / 首帧超时 | 程序化动画（R 组 R8） |
| 2 | 当前角色的 PNG 缺失或损坏 | 形象页：该角色卡显示「素材缺失」占位，**不可选中**；如果它是当前选中项 → 首页回落**咕嘎同形态**图 |
| 3 | 咕嘎 PNG 也缺失（理论不会发生） | 角色区渲染内置图标占位（`Icons.sentiment_satisfied_alt`）+ 隐藏台词气泡；首页其余元素不动 |
| — | 是否提示用户 | **不提示**。只 `debugPrint`；debug 构建下形象页底部一行小字显示渲染模式与降级原因 |

**理由**
- 素材缺失是**打包/开发问题**，不是用户操作问题。给用户弹「素材加载失败」，他能做的只有重装，等于把开发事故转成用户投诉。
- 但它必须在发布前被发现 —— 这件事交给验收里的"素材守卫"（C-16 / R-16：断言 7 张 PNG 与 3 个 `.riv` 路径存在或已被声明为可缺失），而不是弹窗。
- 「回落咕嘎」而不是"回落白框"：咕嘎是必带素材，是最后一道保险。

**反面**
- 弹窗提示 + 引导重装：本地优先 App，用户重装 = 数据全丢（虽然有备份，但用户不会先备份）。为一个图形问题赔掉数据，不可接受。

### 决策 9（B9）· 训练 Tab 结构：**模板 | 计划 两段 + 右上角记录入口；不引入时长选择器**

**先纠正一件事**：现有代码里**没有**「三档时长（10/5/23 分钟）」这个东西。`quick_start_page.dart` 是「计划 | 模板 | 历史」三段 + 模板卡，时长来自模板自带的 `minutes` 字段（渲染在推荐卡上）。所以这不是"保留还是改"，而是"要不要新增"。

**结论：不新增。** 本期训练页不做时长选择器。

| 位置（从上到下） | 内容 | 来源 |
|---|---|---|
| ① AppBar | 标题「训练」+ 右侧两个 action：[记录 `Icons.history`] [新建模板 `+`] | 新增 |
| ② 分段 | **模板 \| 计划**（三段 → 两段，「历史」下线） | 改 `quick_start_page.dart` |
| ③ 模板区 | 类型/难度 chips + 我的模板 + 推荐模板 | 原样复用（`TemplateFilterBar` / `MyTemplatesSection` / `RecommendedSection`） |
| ④ 计划区 | 现有 `PlanSegment` | 原样复用 |
| — | **无 FAB** | 删（新建模板走 AppBar 的 `+`） |

**理由**
- 训练页要回答的唯一问题是"现在练什么"。"练多久"是第二个问题，把它提前到开练之前，等于在"选内容"和"开始练"之间**插一道选择题**，而这道题模板自己已经答了（每张卡上有 12/15/20 分钟）。
- `PROJECT.md` 定位红线写得很清楚：不做"多天训练计划编排"、不做"复杂周期化"。三档时长选择器很容易长成"按我的时间生成一次训练"——那是一整套推荐算法，不在本期。
- 如果将来要做，**判据先立好**：三档时长必须各自映射到一组**已存在**的模板（不能凭空生成训练内容）。判据不成立就不做。

**反面**
- 加"10/5/23 分钟"三按钮：三个按钮各自需要一组对应的训练内容（谁来配？），配不齐就是"点了 5 分钟，给你一个 20 分钟的模板"。
- 保留三段：记录在训练页里就还是一条"看过去"的路，与本期目标 2 直接冲突。

### 决策 10（B10）· 记录页结构：**三块（周日期条 → 本周摘要 → 当天明细），改造不重写**

**结论**

| 块 | 内容 | 处置 |
|---|---|---|
| ① 周日期条 | 周一~周日 + 双色点（橙=训练/蓝=称重）+ 左右翻周 | **复用** `WorkoutListPage._WeekStrip`（改成公开 widget `WorkoutWeekStrip`） |
| ② 本周摘要 | 3 个数字：本周练了 N 次 / 共 M 分钟 / 连续 W 周有训练 + 「看统计」按钮 | **新增**（纯计算，无新表、无新 provider 真实数据源，从 `workoutHistoryProvider` 派生） |
| ③ 当天明细 | 选中日的训练卡列表 | **复用** `_WorkoutCard`（提成 `workout_record_card.dart`） |

| 与现有页的关系 | 结论 |
|---|---|
| `WorkoutListPage` | **就地改造**成记录页（路由 `/workout/records`），不重写。它本来就是这个结构 |
| `WorkoutStatsPage`（`/workout/stats`） | **不动**。记录页只放 3 个数字 + 入口，不搬图表 |
| `HistorySegment` | **删除整个文件**（决策 12） |
| 文件行数 | 改造后必须每文件 ≤300 行（现 `workout_list_page.dart` 485 行）→ 拆成 4 个文件：`workout_records_page.dart` / `workout_week_strip.dart` / `workout_record_card.dart` / `workout_week_summary.dart` |

**理由**
- 现有记录页的结构（周条 + 明细）本身是对的，缺的只是"本周概览"和"它被放在了 Tab 上"。重写等于把踩过的坑（跨月翻周、同日多条、称重/训练双标记）再踩一遍。
- 统计不放进来：`workout_stats_page` 561 行、有 PR/容量等重内容，搬进记录页会让记录页变成第二个大文件。**两个页面各管一件事**。
- 必须拆文件：485 行改造后只会更长，硬顶 300 行纪律。

**反面**
- 重写一个"记录页"：删掉 `WorkoutListPage` 再新建 `WorkoutRecordsPage`，看起来干净，实际是把日历跨周、同日多次训练排序、称重标记这些边界逻辑重新写一遍，且这次没有测试保护。
- 把图表塞进来：记录页要滚动三屏才能看到"某天练了什么"，而用户来这里的第一个需求是"看某天"。

### 决策 11（B11）· 双入口与"再练一次"

**结论**

| 入口 | 位置 | 文案 / tooltip | 跳转 |
|---|---|---|---|
| ① | 训练页 AppBar 右上角（第一个 action） | `Icons.history`，tooltip「训练记录」 | push `/workout/records` |
| ② | 我的 → 我的档案 → 第 4 个 tile | 标题「训练记录」，subtitle「练了几次、哪些天练的」，`Icons.event_note` | push `/workout/records` |

**"再练一次"：能，但只在详情页。**

| 项 | 结论 |
|---|---|
| 路径 | 记录页 → 点训练卡 → `/workout/{id}` 详情页 → 底部「再练一次」→ `/workout/active` |
| 预填什么 | 动作（`exerciseId/name/category`）、目标组数、目标次数、目标时长 |
| **不预填什么** | **重量** |
| 卡片上放按钮吗 | 不放（整卡已经是点击热区） |

**理由**
- 卡片整块可点，再叠一个按钮 = 两个热区打架，误触率高；详情页有空间写清"会把上次的 5 个动作、12 组带过去"。
- 不预填重量：上次能做 ≠ 这次能做。预填重量是"受伤"和"数据造假"（用户直接点完成）两个坑的共同源头。
- 空态按钮不进详情页，直接回训练 Tab（`context.go('/workout')`，**不是 push** —— push 到 Tab 路由会把底部导航叠掉）。

**反面**
- 卡片右侧放"再练"图标：卡片已经有 `chevron_right` 表示"进详情"，两个右向元素指向两个行为，用户会点错。

### 决策 12（B12）· 「历史」入口怎么处理：**删除**

**结论**

| 对象 | 处置 |
|---|---|
| `quick_start_page.dart` 的「历史」分段 | 删除（三段 → 两段） |
| `history_segment.dart` | **整个文件删除** |
| 指向训练记录页的入口 | 只剩 2 个（决策 11），都 push 同一路由 `/workout/records` |
| 是否会两个入口指向同一页面 | 会（就是那 2 个），但它们**同为显性入口、语义相同**（都是"训练记录"），不是两个不同名字的旧页面 |

**理由**
- 现在同一份 `workoutHistoryProvider` 有两套渲染：`WorkoutListPage` 显示「N 组」，`HistorySegment` 显示「N/M 组」。同一件事两种口径**已经发生**，这就是"两套列表逻辑"的实际代价。
- 保留并改名「记录」更糟：训练页会出现一个叫"记录"的分段，右上角还有一个"记录"图标，两条路到一个地方 —— 多出来的那条迟早长歪（改一处忘一处）。

**反面**
- 保留「历史」作为"最近 10 条"的快速视图：那它和记录页的区别是什么？回答不出来就说明它只是历史包袱。

### 决策 14（C14）· 哪些状态用 Rive：**只有首页角色区**

**结论**

| 位置 | 尺寸 | 渲染方式 |
|---|---|---|
| 首页角色区 | 高 195 | **Rive 优先** → 程序化降级 |
| 首页问候区圆形小头像 | ~40 | 静态 PNG（不用 Rive） |
| 趋势页「我的○○」卡 | 118 | 静态 PNG |
| 教练聊天页头像 | 小 | 静态 PNG |
| 形象页 3 张角色卡 | 中 | 静态 PNG（**不要**同屏起 3 个 controller） |

**Rive 状态机契约（作者在 Rive 编辑器里按此实现）**

输入（Flutter → Rive）

| 名 | 类型 | 值域 | 何时发 | 缺失时 |
|---|---|---|---|---|
| `tap` | Trigger | — | 点角色本体 | 忽略（不崩） |
| `speaking` | Boolean | true / false | 台词气泡出现 / 消失 | 忽略 |
| `form` | Number | **1 / 2 / 3** | 形态升级后的第一帧 | 忽略 |
| `celebrate` | Trigger | — | 形态升级瞬间（与 `form` 同帧） | 忽略 |

输出（Rive → Flutter）

| 名 | 类型 | 用途 | 缺失时 |
|---|---|---|---|
| `react_end` | Rive event | 点击动作播完，恢复可点 | Flutter 用 **1.5s 超时**兜底 |

状态（state machine 名固定 `main`，内部状态）

| 状态 | 进入 | 退出 | 约束 |
|---|---|---|---|
| `idle` | 默认 / 所有一次性状态结束 | — | 呼吸循环，**必须能无限播放** |
| `tap_react` | `tap` | 动画自身 exit time | 时长 ≤1.5s；与 `celebrate` 互斥 |
| `celebrate` | `celebrate` | 动画自身 exit time | 时长 ≤2.0s |
| （不用独立 `speaking` 状态） | — | — | `speaking` 用布尔驱动混合（轻微点头/口型），**不许**做成会打断 `tap_react` 的状态 |

**不用 Rive 的**：页面/路由切换、列表滚动、气泡弹出、主题色、文字。**Rive 只画角色本体，不画气泡、不画文字。**

**理由**
- 一个 controller 常驻（首页），是"不泄漏 + 不爆内存 + 不掉帧"最简单的解。三张形象卡各起一个 state machine，是最容易踩到"同屏 3 个 controller 抢 vsync"的写法，而收益是"用户在选形象时看到 3 个都在呼吸"。
- `form` 用 Number 而不是换 artboard：一个 `.riv` 内部按 `form` 切外观，作者在编辑器里一次搞定，Flutter 侧不用管 artboard 名。

**反面**
- 形象页 3 卡都上 Rive：一个页面上 3 个 state machine + 3 张纹理，中端机首帧会掉到 30fps 以下，而且用户在这个页面停留通常 <10 秒。
- 让 Rive 画气泡文字：字体、字号、主题色、i18n 全部失控（Rive 里的文字是矢量描边，不是 `Text`）。

### 决策 15（C15）· 降级：**四级静默降级，只在 debug 构建可诊断**

**结论**

| 顺序 | 触发 | 降落到 | 用户感知 |
|---|---|---|---|
| 1 | `.riv` 文件不存在（`rootBundle.load` 抛错） | 程序化动画 | 无差异 |
| 2 | 存在但解析失败（`RiveException` / 数据损坏） | 程序化动画 | 无差异 |
| 3 | 版本不兼容（数据版本 > 运行时支持） | 程序化动画 | 无差异 |
| 4 | 首帧超时（>500ms 未出帧） | 程序化动画 | 无差异 |
| — | 是否提示用户 | **不提示** | — |
| — | 是否上报/记库 | 不记库；`debugPrint` 一行；debug 构建下形象页底部小字显示「动效：Rive / 程序化（原因）」 | 仅开发者 |

**理由**
- 降级后的体验必须**等价可用**（R10 规定点击/台词行为完全一致），所以用户没有"缺了什么"的感受 —— 没有感受就不需要提示。
- 反过来说：如果降级后用户能察觉差异，那说明程序化动画做得不够好，该修的是动画，不是一个提示条。
- "用户在设置里能看到降级原因"是开发期信息，`kDebugMode` 一个判断就够，不进数据库、不进导出包。

**反面**
- 提示「当前设备不支持高级动效」：这句话对一个只想看自己角色的用户毫无信息量，且暗示"你的手机不行"。
- 静默 + 连日志都不打：线上出现"所有人都是程序化动画"这种事故时无从定位（所以保留 `debugPrint` + debug 小字）。

### 决策 16（C16）· 性能与包体红线（数字）

**结论**

| 项 | 红线 | 怎么量 |
|---|---|---|
| 单个 `.riv` | ≤ **300 KB** | 文件大小 |
| 同屏 `.riv` 数量 | ≤ **1** 个 controller | 代码走查 + 计数器（R11） |
| 角色区首帧（本地 asset 解码到出图） | ≤ **300 ms**（p50，中端机） | DevTools timeline |
| 待机动画帧率 | ≥ **50 fps**，p95 帧时间 ≤20ms | DevTools |
| 角色区内存增量（vs 纯静态 PNG） | ≤ **30 MB** | DevTools memory + Rive 纹理 |
| 冷启动到首页可交互 | ≤ **1.5 s** | 现状基线不得变差 |
| 立绘 PNG 长边 | ≤ **1200 px** | 文件属性 |
| 单张立绘 PNG | ≤ **400 KB** | 文件大小（现有 200~530 KB，新素材按 400 卡） |
| 单角色三形态 PNG 合计 | ≤ **1.2 MB** | 求和 |
| 本期新增素材总增量（7 张 PNG + ≤3 个 `.riv`） | ≤ **3 MB** | APK 体积差 |

**理由**
- 现有 `assets/` 里已有 **8 MB** 立绘（`guga` 2.7M + `guga2d` 1M + `guga3d` 4.4M，其中 `guga/` 与 `guga2d/` 全库无引用），再裸加 7 张大图 + Rive 会直接反映在 APK 上。
- 立绘显示高度只有 195 逻辑像素，1200px 长边已经是 3.5x 密度上限（现图 680px 就是按这个来的）。再大是给不存在的高分屏准备。
- 首帧 300ms 是"用户不会觉得卡"的临界；超过它，用户会先看到布局再看到角色，观感是"图片加载慢了"。

**反面**
- 不设限：三张设定稿直接抠图导出（手机拍摄的设定稿动辄 3000px、单张 2~3MB），7 张就是 15MB，APK 从 40MB 变 55MB。

### 决策 17（C17）· 点击冲突：**角色本体 = 播动作；气泡 = 进对话；长按 = 形象页**

**结论**

| 手势 | 作用 | 是否跳页 |
|---|---|---|
| 点角色本体（195px 立绘区域） | 播 `tap` 动作 + 轻震动 + 换一句台词 | **不跳** |
| 点台词气泡（整块） | 进 AI 教练 `/ai/coach` | 跳 |
| 长按角色（500ms） | 进「我的形象」 | 跳 |
| 动作播放中再点 | **不重启动画**，只换台词 | 不跳 |

**理由**
- 现状把两件事压在同一个 `onTap` 上（`guga_puppet.dart:80-84` 里 `_tap.forward()` 和 `onTap()` 同时执行）—— 接了 Rive 之后，用户点一下会"播了 0.1 秒动作然后页面跳走"，动效等于白接。
- 气泡本来的视觉暗示就是入口：它有 `isChatEntry: true` 的主题色描边 + `chat_bubble_outline` 图标 + 文案「点我聊聊，我在听」。把"聊天"这件事明确交给气泡，是把**已经存在的暗示兑现**，不是新增认知。
- 防抖：`tap_react` 是 1.2~1.5s 的一次性动画，连点时如果每次都 `forward(from: 0)`，动画会一直是第一帧 —— 看起来像卡住了。

**反面**
- 点角色既不播动作又直接跳走（现状）：Rive 接了也看不见。
- 点角色播动作 + 再点一次进对话（双击）：双击在触屏上永远有一半人做不出来，且与长按冲突。

## 八、边界与失败路径

| 场景 | 行为 |
|---|---|
| `character_id` 是未知值（未来角色 / 手改 DB） | 渲染咕嘎，**不回写**（C4） |
| 用户在新版本切到"未来角色"后又装回旧版 | 显示咕嘎；再升回新版本时原选择还在（因为没被覆写） |
| 一段时间没称重，`body_metrics` 只有 1 条 | 历史最大减重 = 0 → form 1；不崩、不显示「再减 NaN 斤」 |
| 一条 `body_metrics` 都没有 | 同上，form 1 |
| 非当天称重后体重涨回 | 形态不回退（只升不降，C7） |
| 用户删掉最低点那条体重记录 | 形态可能回退（允许，自愈，不做补偿） |
| 切角色时正好在播 Rive 动作 | 丢弃，重建 controller（C6） |
| 连续快速切换 3 个角色 | 最后一次生效；不允许出现两个 controller 同时活着（R11） |
| 形象页点当前已选角色 | 无操作（不重复写库、不弹提示） |
| 形象页点"素材缺失"的卡 | 无操作（不可选中、可长按看 tooltip「素材缺失」） |
| `.riv` 存在但 state machine 名不是 `main` | 降级（R5），静默 |
| `.riv` 存在但没有 `tap` 输入 | 用 Rive 播待机，点击时**只换台词 + 震动**，不降级（R5「输入缺失忽略」） |
| `.riv` 首帧 500ms 未出图 | 降级，并且**不重试本次会话**（下次进首页再判一次，见 6.2） |
| 点角色时台词气泡正在显示 | 换一句新的，气泡不消失（R16 的 `speaking` 保持 true） |
| 点气泡 | 进 `/ai/coach`；不进形象页、不播动作 |
| 长按角色 | 进 `/settings/character`；不播动作、不进对话 |
| 记录页翻到未来周 | 允许翻（现有行为），未来日期显示空态 |
| 记录页在某些时区/跨年边界 | 用真实日期算周起点，不用"第几周"编号 |
| 从空态点「现在去练」 | `context.go('/workout')`，**不 push**，避免底部导航叠两层 |
| 「再练一次」时该记录没有任何 sets（理论不会发生） | 按钮置灰 + tooltip「这条记录没有动作明细」 |
| 老深链 `/workout/quick-start` | redirect → `/workout`，不白屏（T18） |
| 老深链 `/workout/stats` | 不变，仍可用 |
| `rive` 加载抛 OOM | 进程级错误，不做处理（不 try/catch 掩盖）；其它任何异常走 R8 降级 |
