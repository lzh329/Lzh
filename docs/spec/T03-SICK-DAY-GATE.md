## 一、产品决策

### 决策 1 · 信号来源：两条路都要，但手动是「必要路径」，AI 是「可选增强」

**结论：选 (c)。** 两条写入路径合并到同一张表的同一行，用 `source` 区分：用户手动开关写 `source='user'`，AI 判断后调工具写 `source='ai_health'`。
**手动开关必须无条件可用**，不依赖任何 AI 配置；AI 那条路没配 Key 就直接不存在，功能不受影响。

**理由：** 这是离线优先 App。只做 AI，等于多数用户没有这个功能；只做手动，用户在 AI 对话里说「我今天发烧了」，教练只能回一句「多喝热水」，用户还得自己去设置页翻开关——AI 就成了摆设。
两条路指向同一行数据，才有统一的撤销与统一的口径。

**反面：如果不这么做会怎样**
- 只做 AI → 未配置 API Key 的用户永远看不到这个功能，等于没做。
- 只做手动 → AI 无法闭环，用户说完了还得自己动手，功能形同虚设。
- 两条路各写各的表 / 各写各的行 → 撤销撤不干净，会出现「AI 说已生效但 UI 没变」这种最难查的信任事故。

**落到代码：** 手动入口在首页「今日训练」卡附近或设置页；AI 入口是新增工具（见决策 4 / E 组）。两处最终都调 `DailyOverrideRepository.upsert`（`lib/core/database/daily_override_repository.dart:71`），只是 `source` 不同。

### 决策 2 · 闸门生效范围：「拦」不等于「藏」，分两类语义

**结论：生病当天只做三件事——不打扰、缩组数、放宽热量。计划内容一律照常显示。**

| 对象 | 生病当天的处理 | 「拦」的语义 | 明确不做 |
|---|---|---|---|
| 训练计划内容（动作 / 组数） | **照常完整显示** | 不拦，只加提示 | 不隐藏、不置灰到看不见、不改模板数据 |
| 训练组数（执行值） | 乘 `setsScale`，结果下限 1 组 | 改今天的执行数值 | 不写回 `plan` 表，不改原计划 |
| 热量目标 | 用 `calorieTargetOverride` 替换，**只允许放宽** | 改今天的数值 | 不允许加严（见下） |
| 训练提醒（本地通知） | 当天不触发 | 真拦 | 不动全局提醒开关 |
| 称重提醒（本地通知） | 当天不触发 | 真拦 | 不动全局提醒开关 |
| 喝水提醒 | — | **App 里不存在** | 本期不做，见下方澄清 |
| 宏量评判 `macroJudgement` | — | **当前无任何消费方** | 本期不接，字段留空 |

**关于「热量目标上调」为什么是上调（反直觉，必须说清）：**
生病时用户吃不下，如果还拿平时的缺口口径去衡量，会显示「今天超标/不达标」的假警报，逼用户焦虑。
所以生病当天是**放宽**目标，不是加严。为避免这个功能被反向使用，**写入时强制校验：override 必须 > 0，且不得小于全局目标 `UserSettings.dailyCalorieTarget`**（全局为空时，要求落在 800~5000，与现有 `set_diet_target` 工具的范围一致，见 `lib/features/ai/domain/ai_tool_specs.dart:279`）。
越界直接拒绝写入并给出明确错误，不静默夹紧。

**关于 `setsScale`：** 合法区间 `(0.0, 1.0]`，默认 `0.5`（减半）。越界抛 `ArgumentError`，与 repository 对 `source` 的处理风格保持一致。
**今日组数 = `max(1, (原组数 × setsScale).round())`。下限 1 组是硬规定** —— 缩成 0 组等于把计划抹掉，跟「藏起来」是同一个坑，还会引出空列表 / 除零的边界 bug。

**两处事实澄清（不要按想象实现）：**
1. **App 里没有喝水提醒。** `NotificationService`（`lib/core/services/notification_service.dart`）只有 4 个能力：训练提醒、每日称重提醒、录入体重后反馈、训练进行中常驻通知。搜「喝水」在 `lib/` 下零命中。所以 `reminderPaused` 只管**训练提醒 + 称重提醒**两条。
2. **`macroJudgement` 目前没有任何消费代码**，只有 repository 里的默认值常量。本期不接，别顺手写进验收。

**反面：如果不这么做会怎样**
- 把计划藏起来 → 用户以为数据丢了。**这比不拦更糟**，是本期最需要避免的事故。
- 只加提示不改数值 → 用户看到「你生病了」然后照样被推 4 组深蹲，等于没拦。
- `setsScale` 允许 0 → 训练页出现 0 组，等价于计划消失，且必然踩空列表边界。
- 热量目标允许下调 → 功能变成「AI 劝你少吃」，对一个减脂 App 是饮食风险，不是保护。
- `reminderPaused` 只改 UI 不动通知 → 通知照响，功能形同虚设。

### 决策 3 · 撤销：只有用户能撤，当天随时撤，撤完立刻回到安全态

**结论：**
1. **谁能撤：只有用户。AI 不提供撤销工具。** 撤销入口固定长在「生病模式」横幅上，不藏在设置里。
2. **什么时候能撤：当天任意时刻**，只要当天存在覆盖行。撤销**不需要二次确认**——撤销是「回到安全状态」，不是破坏性操作。
3. **撤了之后怎样：** 调 `clear(date)` 删行 → 组数、热量目标、提醒**立刻全部恢复原值**，横幅消失，不残留任何生病痕迹。
4. **必须在 UI 上写明「仅今天有效，明天自动恢复」。** 覆盖是按天存的，第二天自然失效——这是实现细节，用户不知道。

**理由：** 撤销权必须在人手里，否则 AI 能自己写自己撤，降级机制（决策 4）直接失效。撤销入口必须和「状态提示」放在一起，用户发现误判的那一刻就要能看到出口。

**反面：如果不这么做会怎样**
- AI 也能撤销 → AI 可反复写/撤，误报计数被绕过，降级形同虚设。
- 撤销藏在设置页 → 用户发现误判时找不到出口，只能忍到第二天，期间一直被拦着。
- 撤销要二次确认 → 把「救回数据」做得比「改数据」还难，本末倒置。
- 不写「仅今天」 → 用户把临时状态当成持久设置，第二天训练提醒又响、组数又变了，第一反应是「数据错了」。**这种投诉最难解释，也最伤信任。**

### 决策 4 · 误报计数与降级：采纳你的倾向，补三处修正

**你的倾向合理，采纳：只有 AI 触发（`source='ai_health'`）且被用户撤销，才 +1；用户自己开的不算。**
**阈值定为 3。** 但有三处要修正，理由见下。

#### 修正 1 · 达到阈值后，不是「要确认」，而是「不调工具」

仓库已有铁律：**所有写操作都必须弹确认卡**（见 `lib/features/ai/domain/ai_tool_specs.dart:53-73`，`writeTools` 逐次确认，注释明确「确认闸门没有放宽」）。
所以本工具**从第一天起就必须弹确认卡**，不存在「降级前可以直接生效」的空间——那会违反仓库既有的安全规矩。

因此降级降的是这个：

| | AI 的行为 | 实现 |
|---|---|---|
| 降级前 | 判断出生病 → 弹确认卡 → 用户点确认 → 生效 | 工具在 `defs` 里 |
| 降级后 | **不调工具**，只回一段文字建议，告诉用户手动入口在哪 | 工具从 `defs` 里摘掉，模型看不到就调不了 |

**现成扩展点：** `AiToolSpecs.defsFor({required bool webEnabled})`（`ai_tool_specs.dart:87`）已经在按开关裁剪 schema（联网搜索关了就把 `web_search`/`fetch_url` 摘掉）。降级复用同一套机制即可，加一个 `sickDayEnabled` 参数。

**理由：** 用户已经不信任 AI 的健康判断了，还让 AI 反复弹卡是骚扰。降级后走「只说不做」，是最省 token、最不可能出错的路径，对离线 App 也最合适。

#### 修正 2 · 计数单调不减，不做自动衰减；改由设置页手动清零

不加时间衰减。理由：行为依赖时间流逝，用户无法预测 AI 什么时候恢复，单测还得 fake clock。
**改为：设置页提供一个「重置 AI 健康建议」（清零）入口。** 计数单调不减，但人有兜底。

#### 修正 3 · 计数写失败时，撤销照常完成

与恢复链「标记写失败即中止」的规矩**相反**：这里撤销优先于计数。
撤销是用户的救回动作，不能因为计数写不进去就被卡在生病模式里。少记一次误报只是「AI 晚一点降级」，是可接受的轻微失败；撤销失败是「用户被困住」，不可接受。
**实现：撤销成功后才 +1；+1 抛异常则记录日志并吞掉，绝不影响已完成的撤销。**

#### 附：+1 的精确触发条件（四条同时成立）

1. 被删行的 `source == 'ai_health'`；
2. 删除发生在覆盖行的**同一个自然日**（跨天后覆盖已自动失效，用户没有撤销动作，自然不计）；
3. 撤销确实执行成功（行被删掉了）；
4. 由用户主动触发撤销（AI 无撤销工具，天然满足）。

**实现建议：** 计数用**原子自增 SQL**（`UPDATE user_settings SET ai_health_override_count = ai_health_override_count + 1 WHERE id = 1`），不要 read-modify-write，避免连续撤销两次时的竞态丢计数。

**反面：如果不这么做会怎样**
- 用户手动开的不算误报若改成算 → 用户早上不舒服开了、下午好了关掉，被记成「AI 误报」，AI 背锅，用户莫名其妙。
- 阈值设 1 → 一次误判就永久降级，太脆。
- 计数自动衰减 → 行为不可预测，测试要依赖时间。
- 降级后只是「多问一句」而不是「不调工具」 → 用户已不信任 AI，还被反复弹卡，是骚扰。
- 计数失败也中止撤销 → 用户被困在生病模式里，这是本期第二严重的事故（仅次于「计划被藏」）。
