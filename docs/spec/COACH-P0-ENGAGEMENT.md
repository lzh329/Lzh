# 嘎教练 P0 — 有记忆、会主动、能落地（增量 PRD）

> 增量范围：**只改 AI 教练**。数据层仅新增 2 张表 + 2 个开关列 + 1 个芯片列。
> 本文对齐 `PROJECT.md`（减脂优先 / 无手动版本号）、`DEVELOPMENT_PLAYBOOK.md`（文件行数、异步一律 Riverpod、迁移铁律）、
> `docs/spec/T03-SICK-DAY-GATE.md`（写法与颗粒度：每条规则都必须能被一条测试证伪）。

## 0. 文档约定

### 0.1 本期三个硬边界

1. **不扩功能面**：只做「每周一条主动消息」「结构化记忆」「动作芯片」三件。语音输入、周报"建议→执行→结果"回看、上下文摘要压缩、新增人设风格，**本期一律不做**。
2. **不改现有工具的安全闸门**：现有工具清单、`writeTools` 逐次确认的规矩原样保留。记忆写入**不是工具**（见决策 5），本期不新增工具、不改 `defs`。
3. **不做云端、不做后台任务**：所谓"推送"在本 App 里只有一种含义 —— 本地通知（`NotificationService`）。App 没运行时**不会**生成任何内容，这条限制决定了下面所有关于"什么时间生成"的规则。

### 0.2 计数口径

- 规则编号与验收编号**一一对应**（`W3` ↔ `W-3`）。规则表说"要什么"，验收表说"怎么证伪"。
- 优先级：**P0 = 本期必须做且必须可测；P1 = 结构留好、本期不做；P2 = 只记录**。
- 所有时间以 `tz.local = Asia/Shanghai` 计算（沿用 `NotificationService.init()` 的既有设定）。
- "本周" = 周一 00:00 起算；"上周" = 本周一往前推 7 天的那一整周。

## 一、背景与问题

嘎教练现在是一个**只能被动应答**的对话框：数据注入做得不错（`AiPromptBuilder` 四层 prompt + `_dataLines` 真实数字），工具链也扎实（工具清单齐全、写操作逐次确认、失败必回执）。但它有三个结构性缺口：

| 缺口 | 现状证据 | 用户感受 |
|---|---|---|
| **不会主动找人** | 入口只有首页咕嘎卡片 → `/ai/coach`（`dashboard_page.dart:129`）。用户不问，教练永远不说话 | "它是个百度搜索框，不是教练" |
| **记不住事** | 每轮 system prompt 都是全量重建（`ai_chat_notifier.dart:186`），只注入当轮数据。上周说过"我右膝有旧伤"、"晚上九点后不吃东西"，下一周再聊，教练完全不提 | "每次都要重新自我介绍" |
| **答完就断了** | 模型给完建议，用户想要执行得自己退出对话、自己找页面、自己点录入 | "说得挺好，可我不想动" |

而这三件事**恰好是减脂用户最需要教练的地方**：减脂不是知识题，是持续性题。缺的不是"再多知道一点"，是"有人记得我上周干了什么，并且现在告诉我下一步做什么，而且一步就能做完"。

**为什么现在做**：单用户自用、本地无云，AI 调用成本可忽略（每周 1 次主动 + 每次对话 1 次轻量抽取）；`NotificationService` / `ReminderScheduler` / `DailyOverrides` 三套基础设施都已就位（T03 刚做完），主动消息可以直接复用排期与闸门，不需要新造轮子。

## 二、目标 / 非目标

### 2.1 目标（3 个，正交）

1. **让教练每周主动开口一次，且这条消息里的每个数字都能在 App 里找到出处。** 不编造、不喊口号、不追责。
2. **让用户看得见教练记住了什么、并能一键删掉。** 记忆是"用户说过的话"，不是"AI 的推断"，永远可审计。
3. **让一次回答到一次行动之间少走两步。** 建议后面挂 1~3 个可点动作，点了就到页面或弹录入，不再付一次模型费用。

### 2.2 非目标（明确不做，别顺手加）

| 不做 | 理由 |
|---|---|
| 语音输入 / 语音播报 | 与"少走两步"无关，成本高 |
| 周报"建议→执行→结果"回看闭环 | 是 P1 的 `WeeklyReportCache` 的活，本期不接 |
| 上下文摘要压缩（长对话压缩） | 与记忆是两件事；摘要不解决"跨周记不住" |
| 新增人设风格 / 新的 `aiStyle` 档位 | 人设已经够用，缺的不是语气 |
| 主动消息里做医疗判断 | 沿用 prompt 红线（`_rules`：涉及伤病只提醒就医，不判断病因） |
| 通知点击深链到具体对话 | P1（见 W15）；首页就有气泡，深链收益低 |
| 记忆逐条"是否允许发送"勾选 | P2，本期只给总开关 + 页头说明 |

## 三、用户故事

1. **周一早上**：As 一个连续练了三周的用户，I want 早上看到一条话，告诉我上周练了几次、体重怎么走的，以及这周做一件什么小事，so that 我不用自己翻趋势页去拼数据。
2. **断网的周一**：As 一个没配 API Key / 正在地铁里的用户，I want 这条消息照样出现，数字照样真，so that 我不会因为"AI 没回"就丢掉这个功能。
3. **练完那一刻**：As 一个刚保存完训练的用户，I want 咕嘎旁边冒一句具体的话（不是"继续加油"），so that 我有被看见的感觉，而且能一键让它展开说。
4. **第二周**：As 一个上周说过"我右膝有旧伤"的用户，I want 这周它给的方案（比如跳箱）已经避开了深蹲类动作，so that 我不用每次重新交代。
5. **查账**：As 一个在意隐私的用户，I want 在设置里看到教练到底记住了我哪几句，并把不想要的那条删掉，so that 我敢跟它说真话。
6. **不耐烦**：As 一个看到"该称重了"但懒得点进体重页的用户，I want 回复后面直接有个「记体重」的按钮，点了就弹录入框，so that 我三秒就记完了。

## 四、产品决策（8 条，全部给结论）

### 决策 1 · 周消息的内容从哪来：**AI 生成 + 模板兜底，且推的是"上周"不是"本周"**

**结论：** 双路径，模板是必要路径，AI 是可选增强。

**关键前提（决定了所有规则）**：本地通知的内容必须在 **App 正在运行时**预先算好并交给 `zonedSchedule`。App 没运行 = 不会生成 = 推不出去。所以"周一 09:00 实时生成"这条路不存在。

由此推出一个必须改口径的结论：**周一推的必须是「上周（上周一~上周日）的总结」**，而不是"本周总结"。理由：
- 周一早上 09:00 时，"本周"才过了 9 个小时，本周体重变化、本周训练次数几乎全是 0 或空 —— 推出去就是"你这周还没动"，等于每周一早上递一张白卷。
- 上周的数据在此时**已经完整且不会再变**，生成出来的每个数字都是终值，不会"推完两小时后又变了"，也就不存在"通知里的数字和 App 里的对不上"这种最伤信任的事故。

如果产品一定要"本周目标"这个措辞，就按下面的方式说人话：**一句话总结上周 + 一个本周要做的小目标**。这样"上周有依据、本周有指向"，且技术上可实现。

**降级链（按序判定，命中即停）：**

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 无 API Key（`AiService.resolveKey` 为 null） | 模板 |
| 2 | 本轮生成超时（15 秒） / 网络异常 / 401 / 余额不足 | 模板，**不重试、不排队** |
| 3 | 返回正文 < 40 字或 > 120 字 | 模板（<40 说明敷衍，>120 系统通知看不全） |
| 4 | 正文命中禁用词（`保证`、`一定能`、`肯定瘦`、`包瘦`、`暴瘦`、`一周瘦`、`几天就`） | 模板 |
| 5 | 以上都过 | AI 正文（`source='ai'`） |

模板必须有降级兜底，因为这是本地优先 App：只做 AI，等于多数用户（没配 Key 的）永远收不到这条消息，功能白做。而只做模板、不给 AI 机会，则浪费了已经注入的数据与风格设定 —— 用户调了半天"豆包感"，收却收到一条系统公告腔，会很割裂。

**反面：只做 AI 会怎样**
- 没配 Key 的用户永远看不到这个功能，等于没做。
- 断网 / 模型抽风的那一周直接静默 —— 而"每周一都有"恰恰是这类功能唯一的信任来源，断一次就没人再期待第二次。
- 不设超时：模型卡 30 秒会阻塞 App 启动钩子（生成发生在启动/回前台），直接拖慢首屏。

### 决策 2 · 推送时机与去重：**周一 09:00，一周一条，读过的就不再推**

**结论：**

| 项 | 结论 | 为什么 |
|---|---|---|
| 时间 | 周一 09:00（本地时区） | 周一早高峰之后、上班还没进入状态；比现有称重提醒默认 08:00 晚一小时 |
| 与日常提醒共存 | 若用户 `reminderHour == 9`，周消息顺延到 10:00 | 同一小时两条通知 = 一次打扰变两次，用户会直接关掉通知权限 |
| 每周条数 | **1 条**（硬上限） | 每周 1 条是"有人在管我"；每周 2 条以上就是"又来催" |
| 去重键 | `weekly:{YYYY-MM-DD}`，取该周周一日期 | 日期是唯一不会漂的东西。用"第几周"编号会在跨年 / 时区上出错 |
| 保证只发一次 | `coach_proactive_messages.dedupe_key` 上建**唯一索引**，写入靠数据库拒绝重复，不靠代码判断 | 代码判断会遇到"生成两条、排期两次"，唯一索引是最后一道闸 |
| 当日已打开 App | **不推**（消息一旦被渲染就取消已排的通知） | 已经读到的东西再弹一遍，是纯粹的骚扰。用户打开 App 的那一刻需求就满足了 |
| 周一 09:00 已过才打开 | **只内展，不补推** | 迟到的推送是错时噪音（周二早上九点收到"上周总结"会让人以为 App 坏了）。而用户此刻就在 App 里，消息就在首页 |
| 生病（`reminderPaused`） | 见决策 3 | — |

**实现要点（给架构师）：** 通知 id 用 **200 段**（训练提醒占 0 段、称重提醒占 100 段，段位不复用）。取消靠 `cancelById(200)`。

**反面：不做"已读不推"会怎样**
用户 08:10 打开 App，首页气泡已经把这条消息完整读完了；09:00 手机再"叮"一声弹出同样的字。第一次用户会愣一下，第二次就会去关通知权限 —— 而关掉通知权限会连带把训练提醒、称重提醒一起废掉，这是隐形损失。

### 决策 3 · 生病闸门联动：**受它管，但只免推送、不免内容**

**结论：** 周消息的**推送**受 `daily_overrides.reminder_paused` 管，**内容与内展不受管**。三条细则：

1. **生成照旧**：不管今天生不生病，消息照常生成（数据本来就在本地，不生成等于白丢一周的总结）。
2. **推送取消**：若该周周一这一天 `reminderPaused == true` → 不排 09:00 的通知，且**不补推**（不会因为周二康复了就周二补一条）。
3. **在 App 内撤销**：用户在周一 09:00 前打开了生病模式（手动或 AI）→ 若本周通知尚未触发，一并 `cancelById(200)`。这是"撤销"不是"补推"，成本几乎为零，但没有它就会出现"我说了今天不舒服，它还是 9 点准时叮我"。

**理由**：`reminderPaused` 的语义是"今天别打扰我"，周消息是一条打扰，所以归它管。但它的语义**不是**"今天别给我看数据" —— 所以消息本身、首页气泡、教练页卡片都保留。T03 的教训很直接：「拦」不等于「藏」，把东西藏起来会被当成数据丢了。

**反面**：若不联动，最讽刺的一幕是"用户周一发烧按了暂停，09:00 收到一条『上周你只练了 1 次』"。这不是漏了一个分支，这是把一个健康功能做成了糟心事。

### 决策 4 · 训练后点评：**只在首页气泡出现，一律本地模板，点了才进对话**

**结论：**

| 项 | 结论 | 为什么 |
|---|---|---|
| 入口 | **只在首页咕嘎卡片下的气泡**（P0）。训练完成页、训练详情页都不放 | 完成页此刻的主按钮是「保存训练记录」，插一句话会挡住主路径；而训练详情页再放一份，等于同一句话两处要各自处理已读，重复打扰概率翻倍 |
| 生成方式 | **一律本地模板，不调模型** | ① 即时性：保存训练后立刻要出（模型要 3~8 秒）；② 成本：高频用户一周 5 练就是 5 次调用，为了一句"练得不错"不值；③ 场景：训练刚结束是"收尾"，用户要一句话，不是一段话 |
| 想听真点评怎么办 | 点气泡 → 打开 `/ai/coach`，**预填**问题「刚才那次训练你帮我看看」，**不自动发送** | 与仓库既有先例一致（`body_compare_page.dart:165`：预填不自动发，"别替用户做决定"，因为请求要花钱、用户可能想换个问法） |
| 是否推送 | **不推送** | 用户刚练完还在 App 里；推一条"你的训练已完成"毫无信息量 |
| 频率 | 每周最多 2 条，同一天最多 1 条（第二次训练覆盖第一条） | 一天练两次的人不该收到两条点评；一周 5 练的人也不该被 5 句话淹没 |

**文案示例（3 条，按训练形态取，不是随机）：**

| 触发条件 | 文案 |
|---|---|
| 力量类，≥20 分钟 | 「刚那 28 分钟力量练得挺实在。明天腿要是酸，就散散步，别硬上。」 |
| 有氧类，≥20 分钟 | 「跑了 30 分钟，这个量对减脂够用了。今天别再加练，吃够蛋白就行。」 |
| 任一类型，<10 分钟 | 「10 分钟也算练了。这周要是还能挤出一次，就很好。」 |

模板红线（与 `_rules` 一致）：不提"消耗了多少大卡"（估不准，容易被打假）、不承诺减重速度、不用「加油 / 坚持就是胜利」这类口号、不给医疗建议。

**反面**：如果自动发一条 AI 点评 —— 训练刚结束、用户还在喘气，屏幕上开始滚字，且每次训练都触发一次付费调用；用户想关掉只能关整个 AI。如果只放训练完成页（保存前）—— 那时训练数据还没落库，点评用的是会话态，和详情页的数字可能不一致，又是一个"两个口径"的坑。

### 决策 5 · 记忆的写入规则：**只从用户原话抽、必须带原话引用、有 topic 才落库**

**结论：**

**(a) 什么算长期事实（5 类白名单，别的都不记）**

| category | 记什么 | 例子 |
|---|---|---|
| `injury` | 伤病 / 疼痛 / 旧伤 / 手术史 | 「我右膝半月板有旧伤」 |
| `diet` | 忌口 / 过敏 / 不吃 / 只能吃 | 「我不吃香菜」「乳糖不耐」 |
| `schedule` | 作息 / 固定时间 | 「我晚上十点才下班」 |
| `agreement` | 约定 / 承诺 | 「以后晚上不吃主食」 |
| `preference` | 偏好 / 讨厌 | 「我特别讨厌跑步」 |

**(b) 明确不记（写死在规则里，可测）**
- 一次性信息：今天吃了什么、今天多少斤、今天累不累、今天练了多久 —— 这些在 `food_log` / `body_metrics` / `workouts` 里，已经每轮注入。
- 一切数字型身体数据：体重、围度、热量目标。**重复存储必然和真数据打架**，一旦记忆里的体重和首页的不一样，用户会认为 App 在骗他。
- 隐私标识：真实姓名、电话、住址、单位、身份证号。
- 医疗结论：「你有膝关节炎」这类诊断（prompt 红线已禁止，记忆层再挡一次）。

**(c) 由谁抽取：** 一轮对话正常结束后，做**一次**轻量模型调用，输入 = 最近 3 轮 user 原话 + 已有记忆清单 + 5 类白名单，输出 JSON 数组。**不阻塞回复、失败静默、每轮最多 1 次。**

为什么是模型而不是关键词规则：
- 没有 Key 就没有对话，也就不需要记忆 —— 所以"无 Key 时记忆要能工作"这个需求根本不存在，规则兜底是白写的。
- 关键词规则记不准。「我膝盖去年伤过，现在好了」既含关键动作词又是否定，正则判不了；而模型能给出 `action=forget`。
- 模型能同时给出 `quote`，这是最有价值的约束（见下）。

**(d) 每条记忆必须带 `quote`（用户原话片段，≤60 字），拿不到 quote 就不落库。**

这是整条记忆链的**防腐层**：它把"AI 的推断"挡在外面，只允许"用户真说过的话"进来。没有它，模型会把"你说你膝盖不舒服"二次加工成"用户有慢性膝伤"，几轮之后记忆里全是模型自己的幻觉，用户看到会直接关掉这个功能。

**(e) 冲突怎么处理：`category + topic` 是唯一键，同键即覆盖。**

用户改口「我膝盖好了」→ 模型输出该 topic 的 `action=forget` → **删行**（不是追加一条"膝盖已康复"，那会让注入时出现两条互相矛盾的记忆）。
模型给不出 topic → **不写**。宁可少记一条，也不要存一条无法被覆盖的孤儿记忆（它会永远冲突、永远删不干净）。

**(f) 条数上限与注入策略**

| 项 | 结论 | 为什么 |
|---|---|---|
| 总上限 | 20 条 | 超过 20 条，注入就变成"倒垃圾"，模型会开始拿记忆凑字数 |
| 每类上限 | 5 条 | 防某一类（尤其 `diet`）挤满全部名额 |
| 淘汰规则 | 超限时淘汰 `last_used_at` 最早的那条（最久没被注入过） | 「最近没用到」= 最不重要，比"最早的先删"更符合直觉 |
| 例外 | `injury` 类**不参与淘汰** | 伤病是安全信息，被"上次吃火锅"挤掉是事故 |
| 注入条数 | 每轮最多 **8** 条 | prompt 膨胀有成本，且超过 8 条模型就不看了 |
| 注入顺序 | `injury` 全量（≤4）→ `agreement` → `diet` → `schedule` → `preference` 补足 | 安全 > 承诺 > 饮食 > 作息 > 偏好 |
| 注入位置 | 【用户数据】之后、【用户额外约束】之前 | 用户手写约束优先级最高（沿用现有 prompt 结构），记忆是被动事实，放它前面 |

### 决策 6 · 记忆的隐私边界：**可见、可删、可关，清空全部数据必清记忆**

**结论：**

| 项 | 结论 | 为什么 |
|---|---|---|
| 「教练记得的事」页 | 设置 → 教练设定 → 新增入口，独立页面文件 | 语义归属在"教练设定"而不是"我的设置"（那里是身体信息/数据管理）；且 `ai_coach_settings_page.dart` 已 299 行、逼近 300 行纪律上限，**列表 UI 必须另起一个页面文件，不许塞进设定页** |
| 可见性 | 按 5 类分组，每条显示内容 + 记录时间 | 用户要能一眼看到"它到底记了什么"，不是只看条数 |
| 删除单条 | **不弹二次确认**，删完 5 秒内可撤销（SnackBar） | 与 T03 决策 3 同源：删除记忆是"回到安全态"，不是破坏性操作。加二次确认会让用户懒得清理 |
| 记忆开关 | `coach_memory_enabled`，**默认开**。关掉 = 不写、不读、不注入、不在对话里留痕；**数据保留** | 关开关 ≠ 删除。用户可能只想暂停一段时间；真要删有下面那个按钮。如果关掉就删数据，会造成"我手滑关了一下，记忆全没了" |
| 「清除全部记忆」 | 独立按钮，**必须二次确认** | 这个才是删除（不可撤销），与"删单条"是两种操作，确认策略必须不同 |
| `wipe_all_data` | **必须清空 `coach_memories` 与 `coach_proactive_messages`**，加进 `DataWipeService.tableNames` | 已在 `tableNames` 里的 `weekly_report_cache` 注释写得很清楚：记录清了、AI 生成物还留着就是"数据没清干净"。记忆更是如此 —— 它是用户最私密的一段对话内容 |
| 会发给模型吗 | **会**（注入 system prompt）。页头一行说明 + 开关副标题都写明 | 这必须说清。用户以为"记忆存在本地"，实际每轮都会随 prompt 报到 DeepSeek 去。不说，等于埋一颗雷 |

页头说明文案（定稿）：
> 这些是你在对话里亲口说过的话，教练用它记住你。每次对话时会一起发给你的 AI 模型（DeepSeek），不经过我们的服务器。不想要的随时删掉，也可以直接关掉记忆。

### 决策 7 · 动作芯片：**5 个白名单，本地规则生成，零模型调用**

**结论：**

| key | 文案 | 点了去哪 |
|---|---|---|
| `open_workout` | 去开练 | `/workout/quick-start`（有活跃计划则 `/plan/{id}/execute`） |
| `log_weight` | 记体重 | `/body` 并自动弹出录入 |
| `log_food` | 记饮食 | `/diet` 并自动弹出录入 |
| `set_reminder` | 设提醒 | `/settings` 的提醒设置区 |
| `open_trends` | 看趋势 | `/trends` |

**生成依据 = 本轮 assistant 正文关键词 + 本轮工具回执 + 今日是否有对应记录。纯本地判定，可单测，不调第二次模型。**

规则（优先级从高到低，命中即收集，最多 3 个）：
1. 本轮有 `start_workout` 回执且 `ok:false` → `open_workout`
2. 正文含「开练 / 开始训练 / 模板」→ `open_workout`
3. 正文含「体重 / 称重 / 上秤」**且今日无体重记录** → `log_weight`
4. 正文含「吃 / 热量 / 蛋白 / 碳水 / 饮食」**且今日无饮食记录** → `log_food`
5. 正文含「提醒 / 几点 / 早点睡 / 作息」→ `set_reminder`
6. 正文含「趋势 / 进度 / 变化 / 这周 / 上周」→ `open_trends`

**一条都不命中 → 不显示芯片。** 不给固定的兜底芯片（比如永远塞一个「看趋势」）—— 芯片的价值是"这条建议现在就能做"，一旦有一半时候给的是无关按钮，用户就学会无视它，那时它连装饰都算不上，只是噪音。

**为什么不用模型生成：** 每轮多一次调用 = 成本翻倍 + 多 3 秒延迟，换来的是"按钮文案更聪明"—— 收益与代价完全不成比例。而且模型生成的 key 一不留神就是白名单外的，点了没反应是最难查的 bug。

**点击行为：** 直接跳页或弹录入，**不产生模型调用、不写入对话历史**。芯片点过即置灰（本次会话内）。理由：芯片是快捷键，不是对话轮次。如果把"点了记体重"当成一条 user 消息发出去，模型会回一句"好的记上了"——但体重其实还没记（录入框才刚弹出来），这就制造了"AI 说记好了但没记"的事故，而这个事故在本仓库已经发生过一次（2026-10-28）。

### 决策 8 · 成本与打扰的红线

| 红线 | 数值 | 理由 |
|---|---|---|
| 每周推送条数 | ≤ 1 | 超过 1 条 = 从"有人在管我"变成"又来催" |
| 每周点评气泡 | ≤ 2（内展，不推送） | 高频训练者的容忍上限 |
| 周消息 AI 调用 | 每周 ≤ 1 次，失败不重试 | 一次约几分钱，但"失败自动重试"会让断网用户每启动一次就付一次失败成本 |
| 记忆抽取调用 | 每次有 user 消息的对话轮 ≤ 1 次 | 失败静默，不重试 |
| 连续 2 周未读 | **停推**（仍生成、仍内展），用户下次看到消息后清零恢复 | 连续两周没打开这条推送，说明它没价值；继续推就是消耗通知权限。停推但不删内容，用户回来还能看到，不惩罚用户 |
| 记忆注入 | ≤ 8 条 / 轮 | 见决策 5(f) |
| 总开关关闭时 | 生成、推送、AI 调用**全部为 0** | 用户关了就该是真关，不能"关掉后还在后台偷偷算" |

## 六、状态与文案表

### 6.1 周消息状态机

| 状态 | 进入条件 | 用户看到 | 通知 |
|---|---|---|---|
| 无 | 本周还没生成 | 无 | 无 |
| 已生成·未读 | 生成成功，`seen_at == null` | 首页「教练说」气泡；教练页顶部卡片 | 周一 09:00 推（未生病 / 未降频 / 未关开关 / 未超时） |
| 已读 | 被渲染一次 | 气泡消失；教练页卡片保留至下次周消息 | 已排的取消 |
| 生病免推 | 周一 `reminderPaused` | 气泡照常出现 | 不推、不补推 |
| 降频免推 | 连续 2 周未读 | 气泡照常出现 | 不推 |
| 已关闭 | `coach_proactive_enabled == false` | 完全不出现 | 无 |
| 降级为模板 | W8 任一条件命中 | 正常展示（语气与 AI 版略有差异，不标注"降级"） | 正常 |

### 6.2 记忆状态

| 状态 | 显示 |
|---|---|
| 空 | 「教练还没记住什么。你在对话里说过的长期情况（伤病、忌口、作息、约定、偏好）会自动记在这里。」 |
| 有条目 | 5 类分组列表，每组标题带条数（如「忌口 · 2」） |
| 开关关闭 | 列表灰化 + 顶部提示「记忆已关闭，教练不会再记新的，也不会用这些。已有的可以删掉。」 |
| 达到上限 | 新增时提示「已记满 20 条，最早没用到的那条被替换了」 |

### 6.3 文案定稿

**模板周消息（3 条，取一条；`{}` 为数字）**

1. 有训练、有体重变化：「上周练了 {N1} 次，一共 {N2} 分钟，体重从 {N3 前} 走到 {N3 后}。这周先把 {目标句} 做到就行。」
2. 有训练、体重没变化：「上周练了 {N1} 次，一共 {N2} 分钟。体重没动很正常，围度和状态会比秤先变。这周{目标句}。」
3. 没训练：「上周没怎么练，也没关系，减脂是长跑不是短跑。这周{目标句}，练完随手记一下就行。」

**目标句（由 N1 决定，最多两句）**

| 上周训练次数 | 目标句 |
|---|---|
| 0 | 「先练 1 次，10 分钟也算」 |
| 1~2 | 「练 2 次，每次 15 分钟以上」 |
| ≥3 | 「保持 3 次」 |

若 `N6`（上周称重天数）< 3 → 追加一句「顺手记 3 天体重」。

**训练后点评**：见决策 4 的 3 条。

**记忆留痕**：`🧠 已记住：右膝有旧伤 · 晚上十点后不吃东西（可在 教练设定 → 教练记得的事 里删）`

**记忆页页头**：见决策 6 定稿。

**关闭主动消息的确认**：`关了就不再主动说话了。想知道情况的时候，随时来问我。`（不劝阻、不挽留）

### 7.4 迁移与清理（照 playbook 第七章铁律）

1. 新增表用 `createTableIfNotExists`，新增列用 `addColumnIfNotExists`（`migration_helpers.dart`），**不准裸 `m.createTable` / `m.addColumn`**。
2. 纯建表 / 加列**不强制包事务**（playbook 7.4）。
3. 唯一索引与 `@TableIndex` **必须两处定义**（表类上的注解 + 迁移块里的 `CREATE INDEX IF NOT EXISTS`），名字逐字一致。
4. `DataWipeService.tableNames` 追加 `'coach_memories'`、`'coach_proactive_messages'`（顺序：无父子约束，追加到 `weekly_report_cache` 之前即可）。
5. 验收：空库安装 + 旧库升级两条路径都手测（playbook 7.7）。

## 八、边界与失败路径

| 场景 | 行为 |
|---|---|
| 没有 API Key | 周消息走模板；记忆抽取不触发（无对话）；芯片照常工作（纯本地） |
| 断网 / 模型 401 / 超时 >15s | 周消息落模板，`source='template'`，不重试、不给用户看错误 |
| 模型返回空 / <40 字 / >120 字 / 含禁用词 | 落模板（W8） |
| 周消息写入 DB 失败 | 什么都不做，下次启动钩子再试。不影响启动 |
| 记忆写入失败 | 吞异常 + `debugPrint`，不影响对话（与 T03「计数写失败不许影响撤销」同思路：锦上添花不能卡住主流程） |
| 记忆抽取超时（15s） | 放弃本轮，不重试 |
| 用户删光记忆 | 注入段整段不出现（不留空标题） |
| 记忆开关关闭 | 不写、不读、不留痕；页头提示；已有数据保留 |
| 系统通知权限被拒 | 周消息不推送，内展照常（不提示用户去开权限，避免变成又一个弹窗） |
| 跨年 / 跨周边界 | `weekStart` 用真实日期计算，不用"第几周"编号 |
| 用户把系统日期改到未来 | 周消息按真实当期生成一次；不做额外防御（与现有提醒一致） |
| 训练完成但退出未保存 | 不生成点评（点评以**已落库**的训练为准，`recap:{workoutId}` 需要 id） |
| 一天练多次 | 同日只保留 1 条点评，后一次覆盖前一次 |
| 无活跃计划时点「去开练」 | 落 `/workout/quick-start`（不报错、不空白） |
| 芯片生成时网络/DB 异常 | 不显示芯片，不影响消息本身 |

外加三条人工走查（写进 PR 描述，每条可一键复现）：
